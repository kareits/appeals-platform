# Document Service

The platform's file boundary: the only service that stores document bytes and their metadata
(root `CLAUDE.md` data ownership, ADR-014, ADR-0012). Other services and the frontend reference a
document by its identifier and never touch the filesystem.

TASK_03A-1 delivers the foundation — metadata, a pluggable `FileStorage` port with a local
filesystem adapter, upload, streamed download, per-appeal listing, and linking a document to an
appeal. Hashing, MIME validation, and antivirus scanning follow in TASK_03A-2; versions, preview,
download audit, and soft deletion in EP-4.

## How it works

- **Contract first.** `contracts/openapi/document-service.v1.yaml` is authoritative; a parity test
  compares the runtime document with it operation by operation.
- **Its own security boundary.** The service verifies IAM-issued access tokens itself (fixed HS256
  allowlist; signature, issuer, audience, expiry, and claim types) and enforces a permission claim
  on every route, so a direct internal call that bypasses the BFF is still authenticated and
  authorized (ADR-0012, following ADR-0008). It imports no IAM code and reads no other service's
  database.
- **Two authorization layers.** First a permission claim: documents are appeal evidence and the IAM
  matrix defines no `document:*` claim yet, so reads require `ticket:read` and writes
  `ticket:update`. Then an object-level decision: the service asks the **Ticket Service**, with the
  caller's own token, what that caller may do with the appeal —
  `GET /api/v1/tickets/{ticketId}/access` → `{canRead, canMutate}`, the same decisions Ticket
  enforces internally (ADR-0008). Reads need `canRead`; **upload and link need `canMutate`**, because
  mutation scope is deliberately narrower: an audit role that may read across teams must not lend its
  breadth to an evidence write (CR-DOC-HIGH-002). A decision is accepted only when it is complete and
  names the appeal that was asked about, so a partial or misrouted answer cannot authorize anything.
  Denied is 403; an unusable or unobtainable decision is **503**, never an implicit allow. A document not yet linked to an appeal is visible to, and modifiable only
  by, its uploader.
- **Untrusted input stays untrusted.** The client filename is sanitized and kept for display only;
  the storage location is a random key generated by the service; the declared content type is
  recorded but never used to serve content.
- **Metadata before bytes.** The metadata row is committed as `UPLOADING` before the first byte is
  written and updated to `AVAILABLE` (or `UPLOAD_FAILED`) afterwards, so an interrupted upload
  leaves a discoverable row rather than an untracked file on the volume.
- **Layered.** `domain/` (storage port, lifecycle, filename and key rules) → `application/` (use
  cases) → `infrastructure/` (storage adapter, persistence, token verification) → `api/` (thin
  routes). No business logic in route handlers.

## API

Base path `/api/v1`; JSON with camelCase fields; RFC 7807 problems; `X-Correlation-ID` propagated.

| Method | Path | Description | Permission |
|---|---|---|---|
| POST | `/documents` | Upload a document (`multipart/form-data`: `file`, optional `ticketId`, `messageId`, `documentTypeCode`) | `ticket:update` + appeal access |
| GET | `/documents?ticketId=&page=&pageSize=` | List an appeal's documents, newest first | `ticket:read` + appeal access |
| GET | `/documents/{documentId}` | Document metadata | `ticket:read` + appeal access |
| GET | `/documents/{documentId}/content` | Stream the content | `ticket:read` + appeal access |
| POST | `/documents/{documentId}/link` | Link the document to an appeal (write-once, atomic) | `ticket:update` + access to both appeals |

Plus `/health/live` and `/health/ready` (readiness covers the database **and** a write probe on the
storage root, so an unmounted or read-only volume marks the instance unready).

Downloads are always served as `application/octet-stream` with `Content-Disposition: attachment` and
`X-Content-Type-Options: nosniff`: uploaded content is untrusted and must never render in the
platform's origin. Safe preview is EP-4.

A document is downloadable only in the `AVAILABLE` status. TASK_03A-2 inserts the scan states before
`AVAILABLE`, which is how docs/06 ("no access before CLEAN") is enforced without changing the
serving path.

## Configuration

Environment variables, prefix `DOCUMENT_` (see the root `.env.example`):

| Variable | Default | Purpose |
|---|---|---|
| `DOCUMENT_ENVIRONMENT` | `local` | Deployment environment name |
| `DOCUMENT_DATABASE_URL` | `sqlite+aiosqlite:///./document_service.db` | Database URL when discrete parts are unset |
| `DOCUMENT_DB_HOST` / `_PORT` / `_USER` / `_PASSWORD` / `_NAME` | unset / `5432` | Discrete PostgreSQL parts; the URL is built with a percent-encoded password, so a secret containing `:@/?#` is safe |
| `DOCUMENT_STORAGE_BACKEND` | `local` | Active backend; only `local` is implemented (ADR-014). Any other value refuses to start |
| `DOCUMENT_STORAGE_ROOT` | `./document-storage` | Directory holding stored objects (a persistent volume in compose) |
| `DOCUMENT_MAX_UPLOAD_BYTES` | `26214400` (25 MiB) | Hard ceiling on the **file** bytes of an upload (multipart framing is not counted) |
| `DOCUMENT_TICKET_BASE_URL` | `http://localhost:8000` | Ticket Service base URL, asked what the caller may do with an appeal. No credentials: the caller's token is forwarded |
| `DOCUMENT_TICKET_SCOPE_TIMEOUT_SECONDS` | `5.0` | Bounded timeout for that decision; a timeout fails closed |
| `DOCUMENT_JWT_SECRET` | dev placeholder | Secret used to verify IAM tokens; **must match** `IAM_JWT_SECRET` |
| `DOCUMENT_JWT_ISSUER` / `_AUDIENCE` | `mfo-iam` / `mfo-appeals` | Expected token claims |

## Owned data

The `document` table (docs/02 document metadata) and the objects under the storage root. The
`sha256` and `scan_status` fields of the data dictionary arrive with TASK_03A-2.

## Local development

```bash
uv sync --all-packages --dev
cd services/document_service && uv run alembic upgrade head   # SQLite by default
uv run uvicorn document_service.main:app --reload
```

Note: when the `uv` binary is not on `PATH`, use `python -m uv …` (see the root README).

## Testing

```bash
uv run pytest services/document_service
```

Covers filename sanitization, storage keys and path-traversal containment, the
upload→list→download acceptance path, the file-byte limit at `limit - 1`/`limit`/`limit + 1`,
lifecycle and linkage rules, authentication and permission negatives, **object-level scope
negatives** (cross-appeal read/download/list/upload/link, **composite roles that may read but not
mutate an appeal**, uploader-only unlinked documents, and fail-closed behavior when the decision is
malformed or unavailable), restart persistence, migrations (including the guarded downgrade),
configuration, and runtime/contract parity (paths, methods, security, status codes, parameters,
response headers, and schemas).

A real-PostgreSQL concurrency test proves the write-once linkage under two simultaneous
transactions. It is destructive, so it is opt-in and target-validated (see the CI job
`document-postgres-concurrency`): set `ALLOW_DESTRUCTIVE_DATABASE_TESTS=1` and
`DOCUMENT_TEST_DATABASE_URL` to a disposable `*_test` database, then run
`uv run pytest services/document_service/tests/test_document_concurrency_postgres.py`.

## Migrations

```bash
cd services/document_service && uv run alembic upgrade head
```

The downgrade **aborts while the `document` table holds rows**: the metadata is the only index of
the files on the volume, and dropping it would orphan them and break the identifiers other services
hold (root `CLAUDE.md`, docs/01, docs/06). No migration deletes stored files in either direction, so
a rollback is reversible by re-running the upgrade.

## Compose deployment

`docker compose -f infrastructure/docker-compose.yml up -d` starts:

- `document_migrate` — a one-shot job that brings the schema to head before the API starts;
- `document_service` — the API, healthy only once its database *and* storage volume are usable,
  with the named volume `document-data` mounted at `/var/lib/appeals/files`.

The service publishes no host port; it is reachable on the internal network (and, in a later task,
through the BFF). `infrastructure/smoke/document_e2e_smoke.py` runs the acceptance path and the
security negatives against the live stack, and CI additionally restarts the container and re-reads
the document to verify that a restart does not lose files.

The image creates `/var/lib/appeals/files` owned by its unprivileged runtime user, and Docker seeds a
**new** named volume from that directory, so a fresh deployment needs no manual step. A volume
created before this image exists may be owned by `root`; chown it once:

```bash
docker run --rm -v appeals-platform_document-data:/data alpine chown -R 1000:1000 /data
```

## Known limitations

- **The Ticket Service is a runtime dependency** of every operation that names an appeal: while it
  is unavailable, documents are unreadable (503). That is deliberate — failing closed — but it means
  a Ticket outage widens to documents.
- **No dedicated `document:*` permissions** until the IAM matrix defines them; appeal permissions are
  reused as the coarse first layer.
- **No request-body ceiling inside the service.** The size limit is exact for file bytes, but the
  multipart body is parsed (and spooled by the ASGI server) before the handler runs, so protection
  against an absurdly large *request* belongs to the ingress/reverse proxy.
- **No content hash, MIME allowlist, or antivirus scan** (TASK_03A-2), and no versions, preview,
  download audit, soft delete, or cleanup jobs (EP-4).
- **Uploads are not idempotent**: a retried upload creates a second document.
- **No `document.*` events yet** — they are emitted in TASK_03A-2 after content verification.
- **Not exposed through the BFF or the frontend**; there is no UI for documents in EP-2.
