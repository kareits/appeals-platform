# SERVICE_MAP — document-service

Structured map of the Document Service. Kept current as behavior changes (Definition of Done, root
`CLAUDE.md`).

## Responsibility

The platform's file boundary (DOCUMENT_SERVICE spec, ADR-014, ADR-0012): the only component that
stores document bytes and their metadata. Every other service and the frontend reference a document
by identifier and never touch the filesystem. TASK_03A-1 covers upload, metadata, streamed download,
per-appeal listing, and linking a document to an appeal.

## Owned data

| Table | Contents |
|---|---|
| `document` | Document metadata (docs/02): identifier, appeal/mail linkage, sanitized filename, storage backend and key, declared content type, size, business type code, version, lifecycle status, uploader, timestamps |

Stored bytes live on the storage backend (`local` in the MVP), addressed by the random
`storage_key`. `ticket_id` and `message_id` are opaque UUID columns with **no** foreign key: the
appeals and mail messages they identify belong to other services' databases (ADR-004). No column
holds file content.

## API

Base path `/api/v1`, JSON camelCase, RFC 7807, `X-Correlation-ID`. Contract:
`contracts/openapi/document-service.v1.yaml`; `tests/test_contract_parity.py` compares the runtime
document with it operation by operation (paths, methods, security, status codes, schemas).

| Method | Path | Description | Permission + scope |
|---|---|---|---|
| POST | `/api/v1/documents` | Upload a document (multipart), optionally linked to an appeal | `ticket:update` + appeal access |
| GET | `/api/v1/documents?ticketId=` | List an appeal's documents (paginated, newest first) | `ticket:read` + appeal access |
| GET | `/api/v1/documents/{documentId}` | Document metadata | `ticket:read` + appeal access |
| GET | `/api/v1/documents/{documentId}/content` | Stream the content as an attachment | `ticket:read` + appeal access |
| POST | `/api/v1/documents/{documentId}/link` | Link the document to an appeal (write-once, atomic) | `ticket:update` + access to both appeals |
| GET | `/health/live` | Liveness | none |
| GET | `/health/ready` | Readiness (database + storage volume) | none |

## Authorization

The service is its own security boundary (ADR-0012, following ADR-0008): it verifies the IAM-issued
token independently (fixed HS256 allowlist; signature, issuer, audience, expiry, claim types) and
enforces a permission claim on every route. It authorizes on **appeal** permissions, because the IAM
matrix defines no `document:*` claim yet: reads require `ticket:read`, writes `ticket:update`. The
uploader (`created_by`) is always the verified token subject, never client input.

**Object-level scope is delegated, not skipped, and reads differ from writes.** After the permission
gate, `domain/scope.py` (the port) and `infrastructure/ticket_scope.py` (the adapter) ask the Ticket
Service — `GET /api/v1/tickets/{ticketId}/access` with the **caller's own token** — what that caller
may do: `{canRead, canMutate}`, computed by the same policy Ticket enforces (ADR-0008). Reads require
`canRead`; upload and link require `canMutate` on every appeal involved, because mutation scope is
narrower and an audit role's breadth must not authorize an evidence write (CR-DOC-HIGH-002). A false
decision becomes 403 with no detail that could confirm the appeal exists; anything that is not a
*complete* decision for *the requested* appeal — timeout, connection failure, non-200 status, wrong
media type, a missing boolean, or a `ticketId` that is absent, malformed, or names another appeal — is
a fail-closed **503**. A document not yet linked to an appeal has no appeal to decide on and is
visible to, and modifiable only by, its uploader.

## Storage

`domain/storage.py` defines the `FileStorage` port; `infrastructure/local_storage.py` implements it
on a local (or network-mounted) filesystem. Keys are `YYYY/MM/<32 hex chars>`, generated by the
service, never derived from client input, never returned by the API, and carry no extension.
Containment is enforced twice: a strict key pattern, then a resolved-path check against the resolved
storage root. Filesystem calls run in worker threads so uploads and downloads stream without
blocking the event loop.

## Document lifecycle

`UPLOADING` → `AVAILABLE` on success, `UPLOAD_FAILED` when writing fails. `PENDING_SCAN`, `CLEAN`,
and `INFECTED` become reachable with antivirus scanning (TASK_03A-2); `DELETED` with soft deletion
(EP-4). Only `AVAILABLE` is downloadable; any other status yields 409, a soft-deleted or unknown
document 404.

## Emitted events

None in TASK_03A-1. `document.uploaded.v1` and `document.available.v1` (ADR-006 catalog) arrive with
TASK_03A-2, after hashing and scanning, so no consumer sees a document before its content is
verified. No event ever carries file bytes.

## Consumed events

None.

## External dependencies

| Dependency | Purpose | Failure behavior |
|---|---|---|
| PostgreSQL (own database) | Document metadata | Readiness fails; requests error |
| Storage volume | Document bytes | Readiness fails (write probe); uploads 500, downloads 500 |
| Ticket Service (`DOCUMENT_TICKET_BASE_URL`) | Object-level read/mutation decision (`getTicketAccess`) | Fail-closed: every operation naming an appeal returns 503 (never an implicit allow) |
| IAM (indirect) | Issues the tokens this service verifies | No runtime call: verification is offline against the shared secret |

## Failure behavior

| Situation | Response |
|---|---|
| Missing/invalid token | 401 + `WWW-Authenticate: Bearer` |
| Missing permission | 403 |
| Appeal outside the caller's read scope (reads) or mutation scope (upload/link) | 403 (non-disclosing) |
| Appeal-scope decision unavailable | 503 |
| Unknown or soft-deleted document | 404 |
| Download of a non-`AVAILABLE` document | 409 |
| Link to a second appeal | 409 |
| File over the size limit | 413 (metadata recorded as `UPLOAD_FAILED`; no readable bytes) |
| Malformed identifier or query | 422 |
| Storage write/read failure, missing stored object | 500 |

## Migrations

Alembic under `migrations/`. `0001` creates `document` with its indexes and the `document_status`
enum. The downgrade aborts while the table holds rows (`infrastructure/migration_guards.py`),
because the metadata is the only index of the files on the volume. **No migration deletes stored
files in either direction.**

## Testing

`pytest services/document_service` — filename sanitization, storage keys and traversal, the
upload→list→download acceptance path, the file-byte limit at `limit - 1`/`limit`/`limit + 1`,
lifecycle and linkage rules, authentication and permission negatives, object-level scope negatives
(including composite read-but-not-mutate roles, fail-closed behavior, and the real adapter against a
mock transport), restart persistence,
migrations, configuration, and runtime/contract parity (including parameters and response headers).
`test_document_concurrency_postgres.py` proves the atomic write-once link against a real PostgreSQL
server (opt-in via `DOCUMENT_TEST_DATABASE_URL`; CI job `document-postgres-concurrency`).
`infrastructure/smoke/document_e2e_smoke.py` runs the acceptance path, the scope negatives, and the
restart check against the real compose stack.

## Known limitations

- **The Ticket Service is a runtime dependency** for every operation naming an appeal; its outage
  makes documents unreadable (503) by design.
- **No `document:*` permissions.** Appeal permissions are reused as the coarse first layer until the
  IAM matrix defines them.
- **No request-body ceiling in the service.** The file-byte limit is exact; protecting against an
  absurdly large multipart *request* belongs to the ingress, because the body is parsed before the
  handler runs.
- **No content hash, MIME allowlist, or antivirus** — TASK_03A-2.
- **No versions, preview, download audit, soft delete, or cleanup jobs** — EP-4.
- **Not exposed through the BFF or the frontend yet**; reachable only on the internal network.
- **Uploads are not idempotent**: a retried upload creates a second document.
- **A storage volume created before this service's image** may be owned by root; chown it once to
  the service's runtime user (see the README).
